# Архитектура шаблона интерактивного курса

GitHub Pages (статический фронтенд) + Firebase Authentication + Cloud Firestore.
Работает на бесплатном тарифе Firebase **Spark** — без Cloud Functions и без привязки карты.

---

## 1. Ключевая идея: что где лежит

GitHub Pages публичен: **любой файл репозитория может открыть кто угодно** (включая `teacher.html`
и весь JS). Поэтому в репозитории лежит только «оболочка» — HTML, CSS и код. Всё, что нужно
скрывать, хранится в Firestore и защищено правилами:

| Что | Где | Кто видит |
|---|---|---|
| Оболочка сайта, код, стили | GitHub Pages (`docs/`) | все |
| Оглавление курса | `units` | все вошедшие |
| Тексты и задания юнита (без ключей) | `unitContent` | преподаватель + группы, для которых юнит открыт |
| Ключи и заметки преподавателя | `answerKeys` | **только преподаватель** |
| Ответы студента | `submissions` | сам студент + преподаватель |
| Результаты проверки | `results` | преподаватель; студент — свой и только после включения проверки |
| Исходный JSON курса с ключами | у вас на компьютере (`content-private/`, в `.gitignore`) | только вы |

> В текущих файлах `index.html` / `teacher.html` ключи зашиты прямо в `teacher.html`.
> На GitHub Pages его сможет открыть любой студент по прямой ссылке — новая схема это исправляет.

## 2. Коллекции Firestore

```
teachers/{uid}            { name }                                  — создаётся ТОЛЬКО в консоли
users/{uid}               { name, email, groupId, createdAt }       — профиль студента
groups/{groupId}          { name, openUnits: [unitId], releasedUnits: [unitId] }
units/{unitId}            { title, order, status: "ready"|"soon", sections: [{id, title}] }
unitContent/{unitId}      { sections: [{ id, title, blocks: [...] }] }    — без ответов
answerKeys/{unitId}       { exercises: { exId: { itemId: answer } }, notes: {...} }
submissions/{unitId__uid} { uid, groupId, unitId, answers: { exId: { itemId: value } },
                            status: "draft"|"submitted", updatedAt, submittedAt }
results/{unitId__uid}     { uid, groupId, unitId, auto: {...}, manual: {...},
                            autoScore, autoMax, manualScore, manualMax, manualPending,
                            score, max, showCorrect, gradedAt }
```

**Почему так:**

- **Роль — отдельная коллекция `teachers`, а не поле `role` в профиле.** Правило `write: if false`
  делает её неизменяемой с клиента. В `users` поля `role` нет вообще, а правила запрещают
  добавлять лишние поля — подделать роль нельзя ни запросом, ни через консоль браузера.
- **Группа = документ с двумя массивами.** `openUnits` управляет доступом к контенту,
  `releasedUnits` — видимостью результатов. Студент подписан на документ своей группы
  (`onSnapshot`), поэтому открытие юнита или включение проверки отражается у него мгновенно.
- **Контент и ключи — разные документы.** Правило на `unitContent` пропускает студента, если юнит
  открыт его группе; на `answerKeys` — никогда. Ключи физически не уходят в браузер студента.
- **Один документ ответов на студента и юнит** (`unitId__uid`). Id предсказуем, правило проверяет,
  что он заканчивается на uid автора, а поле `groupId` совпадает с его реальной группой.
- **Результаты пишет только преподаватель.** Студент не может «поставить себе оценку».

## 3. Как работает проверка без серверного кода

Cloud Functions требуют тарифа Blaze (с привязкой платёжной карты). Поэтому проверку выполняет
**браузер преподавателя** — единственный клиент, которому правила разрешают читать ключи:

1. Студенты заполняют задания, ответы сохраняются как черновик (`status: "draft"`).
2. Студент нажимает «Submit this unit», `status: "submitted"`; правила запрещают дальнейшие правки.
3. Преподаватель нажимает **«Check & release»**:
   - его браузер читает `answerKeys` и все сданные работы группы,
   - сравнивает ответы с ключами (без учёта регистра, лишних пробелов, типа апострофа),
   - записывает `results/{unitId__uid}` для каждого студента,
   - добавляет юнит в `groups/{gid}.releasedUnits`.
4. Студенты подписаны на группу, видят, что проверка включена, загружают свой результат.
   Правила выдают `results` студенту, только если юнит есть в `releasedUnits` его группы.
5. Открытые ответы преподаватель оценивает вручную (балл + комментарий) во вкладке
   «Student work». До включения проверки оценки не видны студенту; после — видны сразу.

Опция «Показывать правильные ответы» решает, попадут ли ключи к ошибкам в `results`
(студент видит ключи только к своим заданиям и только после проверки).

**Ограничение подхода:** после включения проверки сдать или изменить работу нельзя (правила
блокируют запись). Если нужно принять позднюю работу — «Скрыть результаты», студент сдаёт,
затем «Перепроверить». При переходе на Blaze шаг 3 переносится в Cloud Function
(`onCall gradeUnit`), клиентский код меняется в одном месте — функции `releaseUnit`.

## 4. Сохранение «на лету»

- Каждое изменение поля пишется в `localStorage` мгновенно и в Firestore через 1 секунду
  после последнего нажатия (debounce).
- Firestore работает с офлайн-кэшем в IndexedDB (`persistentLocalCache`): если связь пропала
  или вкладку закрыли, запись не теряется и уйдёт на сервер при следующем открытии.
- При уходе со страницы (`visibilitychange` / `pagehide`) черновик сохраняется немедленно.
- При загрузке, если в `localStorage` есть копия новее серверной, она восстанавливается.
- Нагрузка: ~1 запись на паузу в наборе. Группа из 30 человек тратит порядка тысяч записей
  на юнит — в пределах бесплатной квоты Spark (на момент написания — 20 000 записей
  и 50 000 чтений в сутки; актуальные лимиты сверьте на странице тарифов Firebase).

## 5. Аналитика (раздел «Analytics»)

Считается в браузере преподавателя по сданным работам и ключам (по желанию — с черновиками):

- сводка: сколько сдали, средний процент автопроверки, сколько открытых ответов оценено;
- **«Вопросы, вызвавшие наибольшие трудности»** — 10 пунктов с наименьшим % верных ответов,
  с правильным ответом и самыми частыми неверными ответами («is give» ×3, «(пусто)» ×2);
- тепловая карта «студент × упражнение»;
- полный список вопросов;
- по клику — все ответы конкретного студента с подсветкой ошибок.

В разделе «Student work» таблица обновляется в реальном времени, пока студенты работают.

## 6. Структура репозитория

```
docs/                    — публикуется на GitHub Pages
  index.html             страница студента
  teacher.html           кабинет преподавателя
  css/course.css         стили (палитра и типографика исходного курса)
  js/firebase-config.js  конфиг проекта + название курса
  js/fb.js               подключение Firebase SDK (версия — в одном месте)
  js/common.js           отрисовка упражнений, автопроверка, подсчёт баллов
  js/student.js          логика студента
  js/teacher.js          логика преподавателя
  js/shell.js            боковая панель: сворачивание, юниты-аккордеон
firestore.rules          правила безопасности
tests/rules.test.mjs     тесты правил (эмулятор Firestore)
tests/ui.e2e.mjs         сквозной UI-сценарий (Playwright, на мок-Firebase)
tests/mock-fb.js         мок Firebase для UI-теста
.github/workflows/       автозапуск тестов правил на GitHub
content-private/         исходники курса с ключами — НЕ коммитятся (.gitignore)
```

## 7. Что дальше (после болванки)

1. Перенести весь Unit 1 из текущего HTML в JSON-формат (можно автоматизировать скриптом).
2. Дедлайны: поле `deadlines.{unitId}` в группе + проверка `request.time` в правилах.
3. Несколько пропусков в одном предложении (`___` × N) и drag-and-drop для matching.
4. Экспорт ведомости в CSV/Excel из вкладки «Работы».
5. Подтверждение email при регистрации (`sendEmailVerification` + `request.auth.token.email_verified` в правилах).
6. При переходе на Blaze — проверка в Cloud Function и назначение роли через custom claims.
